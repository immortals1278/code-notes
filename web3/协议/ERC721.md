## 使用
`_baseURL()`需要子合约覆写

## ERC165
被721继承
查询合约是否实现某个接口，避免调用不支持的函数导致失败
### supportsInterface
检查当前合约是否支持某个接口。
`return interfaceId == type(IERC721).interfaceId`
`super.supportsInterface` 调用父合约中的 supportsInterface 实现。

## 存储结构
- **`_owners`**：tokenId → 持有人地址
- **`_balances`**：地址 → 该地址拥有的 NFT 数量
- **`_tokenApprovals`**：tokenId → 被授权的单个地址
- **`_operatorApprovals`**：owner → (operator → bool)，记录某地址是否授权给某操作员
如`_operatorApprovals[0xAlice][0xBob] = true`针对一个所有者的所有 NFT

`tokenURI`：指向链下数据的链接（HTTP/IPFS）,图片，名称

### approve
设置“被授权的单个地址”，依旧有两个approve来控制发不发事件

## Mint
两个_safeMint(),有一个要传数据一个没有

`ERC721Utils.checkOnERC721Received(_msgSender(), address(0), to, tokenId, data);`防止代币被转到不支持ERC721的合约里永久锁死。
为什么任何未实现 onERC721Received 函数的合约都不支持 ERC721。没有这个函数，转账成功但合约无法操作该 NFT → 永远困在合约里

## Burn
销毁时“操作者”是 address0 跳过验证权限，因为burn是internal，只能从合约内部调用，“操作者”已经拥有控制权
 
## Transfer
先 _update() ,返回前主人，再判断是不是传入的 From
token id 拿到from地址，检查是否授权给auth（执行者），清空授权，改from和to的balance和token的owner

_safeTransfer()。检查目标合约是否支持ERC721。有两个一个要传数据。

## 检查
一个检查拆成很多个函数：一个函数检查某个数据有没有，这个函数又套在另一个函数里，检查如果没有可能出现的问题，revert不同
